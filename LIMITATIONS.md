# Limitations, Threats to Validity, and Honest Boundaries (`LIMITATIONS.md`)

This document states explicitly what `secmesh-pqsi` does **not** prove, claim, or guarantee.

## 1. Cryptographic & Physical Security Boundaries

1. **Software E91 is a mathematical simulator, NOT physical photonic QKD:**
   Simulating CHSH correlations over classical TCP/localhost validates finite-key admission formulas, adversarial rejection paths (Classical, Aligned, Parked Eve), and key-rate accounting. It does **not** generate physically certified device-independent randomness; physical DI-QKD/QRNG requires loophole-free photonic/atomic Bell-test hardware closing detection, locality, and freedom-of-choice loopholes.
2. **Post-Super-Intelligence (PSI) secrecy requires an independent physical or pre-shared pad:**
   Theorems `T2a` and `T2b` kernel-check the bijection cores (one-time-pad key uniqueness and XOR-combiner factor uniqueness); the probabilistic statement of unconditional secrecy against computationally unbounded adversaries is paper-level (Shannon 1949) and holds only when the information-theoretic key factor $K_{\mathrm{IT}}$ is statistically uniform and independent of adversary knowledge (e.g., from a certified physical QRNG or physically distributed one-time pad). When operated without an external pad, confidentiality rests strictly on the strongest surviving computational primitive (`ML-KEM-768` or `X25519`), and the system never misrepresents computational keys as information-theoretic.
3. **One-time pad discipline for Carter–Wegman $\mathbb{F}_{2^{128}}$ IT-MAC:**
   Theorem `T2d` kernel-checks only the polynomial root bound; the $\le d/2^{128}$ forgery probability is a paper-level consequence and assumes a fresh one-time pad mask $s$ per authenticated frame. `secmesh-pqsi v2.5.0` enforces monotonic 64-bit sequence numbers and an RFC-6479-style bounded sliding replay window (`createReplayWindow` / `verifyCwFrame`) across all Guardian v2 frames; when operated with a pre-shared pad pool (`padPool`), each frame consumes a single-use IT pad (unconditional PSI mode), whereas `padSeed` mode derives per-frame pads via `SHAKE256` (computational Wegman–Carter mode, explicitly distinguished from unconditional PSI).
4. **No hardware side-channel or FIPS 140-3 certification:**
   While constant-time comparison (`secmesh_ct_memeq`) and zeroization (`secmesh_secure_zero`) are implemented in C11, Lean 4 verifies mathematical specifications rather than compiled assembly timing, cache, power, or EM leakage on specific microarchitectures. `secmesh-pqsi` is a research reference implementation, not a FIPS 140-3 validated module.
5. **Simulated mesh defense telemetry vs. live network pentesting:**
   The pre-registered 30-seed paired benchmark (`results/exact_verification_report.json`) evaluates deterministic health-field controller dynamics under synthetic intrusion injection. It is **not** a substitute for live adversarial penetration testing on production network infrastructure.

## 2. Formal Verification & Tooling Boundaries

1. **Zero-Mathlib algebraic boundary:**
   To eliminate Mathlib from the Lean 4.35.0 trusted computing base, transcendental curves (Hoeffding exponential, binary entropy $h(p)$, Bernoulli KL inversion, and trigonometric $\cos/\sin$) are formalized via cleared-denominator integer/rational identities and cross-verified to 60-digit `Decimal` precision in Python and differentially against C11 and Node.js 25 (`< 1e-11`). This substitution applies to every theorem family, not only `T1a`, `T1b`, `T1c` and `T4b`: it also covers `T1e`, `T2c2`, `T3c`, `T4a`, `T4d`, `T4e`, `T6a`, `T7a`, `T7b` and `T7c`.
2. **Physical, probabilistic and protocol objects are not defined in Lean:**
   The Lean code contains only `Int`/`Nat`/`Bool` sums, lists used as polynomials, the home-made `SimpleField` class (instantiated only on `Fin 5`), and fixed matrices. It defines no probability distribution type, entropy, Hilbert space, quantum state or operator, Fisher information, Berry curvature or Chern number, PIR scheme, commitment scheme or EFI pair. Theorem names that mention these objects (for example `t4d_chern_concurrence_entropy_conservation`, `t7a_toner_chsh_monogamy_and_eve_isolation`, `t7b_hiding_binding_conservation_nogo`, `t7c_fuchs_vandegraaff_microcrypt_efi`) describe the paper-level reading. In particular: `T7a` assumes the Toner–Verstraete qubit/anticommutation reduction and an assumed CKW-type relation; `T7c` covers only classical square-integer weights, and its pure-state relation $D_{\mathrm{tr}}^2 + F = 1$ holds by definition; `T4d` is the identity $\cos^2 2\alpha + \sin^2 2\alpha = 1$ in integer form, and $c_{\mathrm{eff}}$ is continuous rather than topological; `T3c` compares two published $K = 1$ PIR rate formulas; `T3b` "tightness" is only the arithmetic $d = 2b$; `T4c1` assumes its conclusion; the first conjunct of `T1e` is $P \to P$; and part 3 of `T6a` adds two assumed bounds rather than proving a Cheeger inequality. The per-family split is in [`CLAIMS.md`](CLAIMS.md).
3. **Lean `Compress_1` model differs from FIPS 203 at one point:**
   `mlkemCompress1` uses offset 1665, while FIPS 203 rounding and the vendored C (`MLKEM_Q/2 = 1664`) use 1664. They differ only at $x = 832$. The `T5c` margin ($|e| \le 831$) never reaches 832 and also holds for FIPS 203, but `adv_compress1_fails_at_plus_832`, the CI negative test and the paper's statement that both $b = 0$ and $b = 1$ fail at $e = +832$ are false for FIPS 203. This is recorded in [`ERRATA.md`](ERRATA.md) and is not yet fixed in the Lean code.
4. **Scope of "zero `sorry`":**
   `lean/PalomarChallenge.lean` holds 28 `sorry` stubs by comparator convention and is not a default build target. There is no `sorry`, `admit` or `native_decide` elsewhere outside comments and docstrings.
5. **Platform split for Lean 4.35 `lean4lean` & `lake comparator` (`problem`):**
   On Windows hosts, the bundled `lean4lean.exe` in `leanprover--lean4---v4.35.0` fails with `incompatible header` and `lake comparator` requires Linux `bwrap` namespaces. Accordingly, Windows local verification runs **5 distinct kernel implementations across 6 runs** (`lean`, `leanchecker`, `leanchecker-paranoid`, `con-leche --verified`, `con-ron --verified`, `nanoda_bin 0.4.19`; `leanchecker` and `leanchecker-paranoid` are one implementation in two modes), while Ubuntu Linux GitHub Actions CI executes `lake comparator --config palomar_comparator.json --paranoid` with **6 kernel runs (5 distinct implementations, including `lean4lean`)**; the Lean paranoid and Lean default runs are one kernel in two modes.
6. **Eshkol v1.3.6 native LLVM binary vs. portable dual-number AD runtime (`problem`):**
   While a Windows `eshkol-run.exe` binary exists on the author's local machine, it exited with `0xC0000135` (`STATUS_DLL_NOT_FOUND`) due to missing runtime DLLs. Rather than leaving the 5 Eshkol modules unexecuted, `secmesh-pqsi v2.5.0` ships a portable, zero-dependency forward-mode dual-number AD & OALR `(with-region ...)` evaluator (`node/src/eshkol-ad-runtime.mjs`) with step/recursion-depth DoS caps that parses and executes all five `eshkol/*.esk` modules live and verifies every AD derivative to `< 1e-12` against closed-form calculus. This portable evaluator is transparently labeled as a reference AD interpreter rather than Tsotchke's native LLVM AOT compiler.
